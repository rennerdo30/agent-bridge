## 1. Decision and invariants

Run one on-demand daemon per OS user and canonical Bridge home, independent of session MCP lifetimes. The final daemon owns one SQLite state store and its only writer connection. MCP, runners, CLI, dashboard, remote adapters and mobile send authenticated commands and consume snapshots/events. They have no durable Bridge job registry, authority cache, archive publication or state-file polling. External CLIs' own transcripts remain external evidence, not Bridge current state.

The required invariants are:

1. Exactly one current authority for an installation/domain. A durable election epoch fences every writer, command, executor registration and side-effect dispatch. A display name, PID, timestamp, cached log or caller-provided session string cannot confer authority.
2. Every current entity has a durable monotonic version; every job turn has an exact generation; every state mutation and its ordered event batch commit in the same transaction. Versions never reset on restart, rename or handoff.
3. A job's supervision, execution, activity and historical evidence are distinct. One logical job can have many immutable turns/runs and one current turn. Missing PID/session or a stored `running` label does not prove death or execution.
4. Readers agree at the same snapshot version. Different sampling times can legitimately differ. An ended session can retain genuinely executing detached jobs. Historical records cannot create a current running badge.
5. All accepted command bytes, conflicting evidence, original stores, unknown fields, message consumption receipts and archives remain retained. Projection collapse and pagination never delete data.
6. Compatibility is negotiated per domain and operation, without a global reader floor, forced reader eviction, forced ownership, automatic cancellation or destructive finalization. Unknown legacy writers cannot authorize unsupported current-state operations.
7. Control work has bounded admission and priority. Bulk parsing, compression, importing and backup preparation cannot run synchronously on the RPC/control loop. No latency guarantee applies to unbounded traffic, arbitrarily slow storage or an unscheduled daemon.

## 3. Process model, lifecycle and authentication

The client bootstrap resolves a canonical physical home and user identity; aliases of the same home map to the same installation. The daemon's persistent `installationId` is independent of filesystem spelling, machine display name, projects and MCP sessions. Home relocation is an explicit verified operation; copied homes do not silently share executor capabilities. No owner-specific path or hostname is embedded in source or RPC.

| Platform | Recommended on-demand lifecycle | Election and local authentication |
| --- | --- | --- |
| Windows | First client starts a background daemon detached from its console/MCP job scope; supervisor ownership must not cause it to die with that scope. No visible window. Service/task registration is optional future packaging, not required for demand start. | Per-user/home native singleton lock and named pipe with current-user access control; authenticate the local principal plus installation challenge/capability. PID alone is insufficient. |
| macOS | First client starts a detached user process; retain it independently of session exit. Optional LaunchAgent later, with owner consent and parity with demand start. | Per-UID/home lock and Unix-domain socket in a verified user-owned private runtime directory; verify local peer credentials and challenge/capability. |
| Linux | Same detached user process; optional user service/socket activation later, without making systemd availability a prerequisite. | Per-UID/home lock, private Unix-domain socket, peer credentials and installation challenge/capability. |

OS wrappers need platform CI proof of detachment, principal verification, stale socket/lock handling and no accidental child-job containment. Token/capability material is never returned in snapshots, events, errors or evidence reports. Mobile/network keep their existing TLS/pair/device authentication; gateways map authenticated principals to scoped daemon capabilities. Local ownership of a Bridge home does not turn untrusted caller parameters into session authority.

Startup: `absent -> booting -> recovering -> serving -> draining -> stopped`; unrecoverable store/identity failure is `unavailable`. Simultaneous bootstraps attempt the OS singleton lock; losers connect/retry with bounded jitter. A socket bind winner is tentative until the durable epoch transaction commits. Before serving, verify store lineage, schema/capabilities and domain migration markers; increment `brokerEpoch` transactionally, register the holder's random instance nonce/process creation identity, and publish a ready handshake with the committed epoch and replay watermark. Recovery can serve cached health/readiness while explicitly reporting domains unavailable; no control is authorized from half-imported data.

The canonical singleton/discovery identity must be protocol-version independent. Current `paths.ts:31–43` deliberately includes protocol version in pipe/socket names, allowing incompatible legacy brokers to coexist. Preserve those old transports as compatibility endpoints only where safe; they cannot elect another authoritative daemon for the same home. Unknown clients still capable of old embedded election are part of the migration barrier, not evidence that one instance already exists. The daemon creates/owns bootstrap metadata and authentication material; clients do not create their own durable authority/token registry.

The lock is held for daemon lifetime. A timeout, wall-clock lease expiry or absent PID alone never authorizes takeover of a live unknown holder. A verified crash releases OS ownership; a new holder commits a strictly greater epoch. Every writer transaction rechecks epoch/instance in the same transaction. An old paused daemon resuming after replacement cannot commit or obtain a new application permit with its old epoch; queued external packets require section 3.1's receiver fence. Losing epoch closes admission; it does not cancel child work. The executor reconnects and explicitly attaches its exact existing run to the new authority after a capability challenge. This is not a new turn/child launch.

The last statement requires receiver-side application fencing, not only a dispatcher check. Section 3.1 defines its readiness barrier: a successor can expose health/snapshots while affected side effects remain unavailable until predecessor attachments and in-flight applications are reconciled. No claim is made that advancing a database epoch retracts a packet already on a native transport.

Planned upgrade/restart is a daemon operation, not an MCP disconnect: drain new mutating admissions, commit a restart barrier/outbox, release the endpoint and lock, then let the new executable acquire a fresh epoch. Clients reconnect using their last cursor and idempotency key. Requests whose response was lost query their committed receipt. No automatic package update, process kill or service registration is authorized by this design. An idle daemon remains available; an eventual idle-shutdown policy must exclude active jobs, approvals, pending delivery and durable waits and receive separate review.

### 3.1 Executor attachment, application permits and successor readiness

The daemon is the issuer of scoped reconnect/attachment capabilities, persisted as restricted credential/verifier records with issuer lineage, principal, run/turn, rights and revocation revision. A capable receiver (runner, inline/native launch host, permission relay or wake endpoint) proves that capability over credential-checked canonical IPC and an instance-nonce challenge. Reattachment rotates its dispatch-channel capability and increments `attachmentGeneration`; rename/session registration change alone grants no executor identity. Handoff may alter supervision/grant revision while keeping the same executor/run; any new dispatch capability is issued explicitly after the receiver acknowledges that revision. Revocation or proven instance replacement blocks old capabilities; mere timeout/PID absence does not establish replacement.

An action frame identifies `{installationId,lineage,brokerEpoch,jobId,turnGeneration,runId,executorInstance,attachmentGeneration,grantRevision,commandId,actionId,payloadDigest,actionKind}`. Receivers validate the authenticated channel, all exact fields and payload bytes. Enqueuing a frame is not application permission. Immediately before application, the receiver uses the canonical daemon connection to request `beginApply(actionId, exactFields)`; the sole writer rechecks current epoch/attachment/grants/turn and commits a one-use application permit. Cached epoch knowledge, a signature from an old daemon, or a queued allow/cancel/launch packet alone cannot authorize application. A lost permit reply is resolved by scoped receipt lookup (section 7.1), not another action ID.

The receiver serializes applications for that execution/permission request, checks the permit again against its installed attachment, and deduplicates action IDs before touching the native side effect. It reports `applied` with exact evidence or `refused_before_apply`; duplicate already-settled requests return the retained outcome from the daemon's application ledger. Launch application settlement acknowledges the exact existing child/launch result, not completion of the child's whole job; established execution can continue across handoff. Thin receivers keep only volatile application state; after receiver failure an unresolved permit is `application_unknown`, and no replay/new launch is allowed unless the native target supplies exact idempotency/effect evidence. SQLite cannot atomically commit an arbitrary native effect; crash between native application and ACK is explicitly unknown, never an exactly-once assertion.

Successor recovery first increments the durable epoch and closes new side-effect admission on affected attachments. It imports all reserved/applying/unsettled predecessor permits. For each receiver it requires an authenticated `quiesce(oldEpoch)` exchange: serialize after any applying action, stop/dequeue unpermitted predecessor frames, report each permit's exact applied/refused/unknown disposition, revoke the old attachment, then acknowledge the new epoch/attachment/grant revision. A receiver paused after obtaining an old permit may still finish that already-reserved application while the successor is recovering; the successor cannot advertise that control/attachment as ready or apply conflicting new actions until it settles. A late old packet without a prior permit fails `beginApply` against the new epoch even before the receiver learns that epoch. If quiescence/settlement cannot be proved, preserve the same executor as unknown and expose `attachment_unavailable`; no forced takeover, cancellation or duplicate launch. This closes the stale-channel race by withholding successor readiness, not by pretending remote application can be undone.

Handoff, grant revocation and permission-term changes also use an application barrier before committing authority changes that invalidate an outstanding permit. Prepared changes do not become authoritative until affected permits are refused/settled or a reviewed native proof establishes their effect. In-flight grants cannot silently survive a committed grant revision. For a receiver unable to implement this contract, affected launch/cancel/allow/wake control stays unsupported/unavailable and its domain cannot promote with a claimed fence. Existing execution and read-only evidence may continue. Barrier acquisition/settlement is asynchronous, bounded by the unchanged RPC deadlines with a durable pending receipt; health and unrelated eligible controls continue. Zero-timeout acceptance requires capable receivers to settle within the disclosed bounded fixture, not unbounded stuck channels.

## 4. One SQLite state store and transaction boundary

Recommended new additive `state-core.db` separates authority from retained 0.30.14 files and avoids making an old binary a writer of the new format. This is an architectural choice for review, not a file created here. One connection in a dedicated writer thread **inside the daemon process** owns all mutations. The RPC/control loop never blocks on synchronous SQLite waits. Read-only connections use WAL snapshots; workers cannot open writable state connections. Schema changes use verified backup/admission, short transactions and explicit domain markers. The final system has one authoritative database; legacy/history/archive artifacts are retained evidence, not another current store.

Logical tables (descriptive schema, not executable DDL):

| Table | Keys, required state and constraints |
| --- | --- |
| `authority` | Singleton installation/store lineage, epoch, instance nonce, durable commit version, schema and per-domain mode/capabilities. Epoch CAS fences transactions. |
| `sessions`, `session_bindings`, `session_registrations`, `session_aliases` | Broker-issued stable session ID, authenticated principal/project identity, optional native-thread binding, registration generation, connection/activity state and entity version. Aliases are scoped lookup evidence, never owner IDs. |
| `jobs` | Installation+logical job ID, original project, immediate supervisor session/job ID, root supervisor session ID, concurrency-root ID, current generation, lifecycle, execution evidence, policy/grant revision and version. One current turn per job. |
| `turns`, `runs`, `executor_attachments` | Unique `(jobId, generation)`, durable allocated generation counter, run ID, lifecycle/version, launch command ID, exact executor capability/instance, process creation evidence when available, start/end facts. One selected execution per admitted turn; unresolved launch acknowledgement blocks another launch. |
| `messages`, `message_routes`, `message_consumption` | Stable message UUID plus exact raw payload digest; current recipient stable identity, route revision, consumption per intended identity and delivery state. Conflicting UUID payloads are retained and rejected, not silently deduplicated by ID. |
| `approvals`, `owner_questions`, `question_answers` | Exact run/tool/request identity, pending terms and version, answer/replay receipt, expiration/dismissal/outbox. Owner-question answer never itself grants native permission. |
| `commands`, `event_batches`, `events`, `outbox`, `application_permits` | Stable authenticated issuer+command ID and immutable request digest, durable receipt; transaction commit version; ordered event index/entity version or immutable verified manifest reference; executor action ID, attachment and applied/refused/unknown settlement. No event or success acknowledgement before commit. |
| `job_mail`, `job_mail_routes`, `job_mail_consumption`, `delivery_claims` | Stage-2 subset of message state: complete report/question envelopes, route revision and identity-bound consumption/hand-out claims. Every ACK/consuming reader participates in the same authority before jobs promotion. General messages may remain legacy until stage 4b. |
| `prepared_changes`, `change_fragments`, `domain_modes`, `legacy_source_modes` | Bounded immutable preparation bytes/manifests, verified dependency revisions and selected current pointer; authority target and source-retention pointers are separate. Only a committed activation header makes prepared changes/current versions visible. |
| `legacy_sources`, `import_chunks`, `evidence_records`, `conflicts` | Physical source identity, generation/snapshot/hash/length/count manifest, exact original payload/raw bytes or immutable contained blob reference, import checkpoint, unknown fields and all conflicting versions. Evidence import cannot overwrite current authority. |
| Auxiliary domain tables | Admission/slot/root reservations, policy/grants, decisions, durable waits, worktree provenance and device/replay registry, as needed for existing behavior. Same daemon writer; no separate client authority introduced while moving six primary domains. |

Counters use checked 64-bit integers serialized as decimal strings in JavaScript-facing RPC; never imprecise JSON numbers. `generation` is allocated in the job transaction, not `Date.now()`. Entity `version` increases on every accepted change of that entity. `commitVersion` increases once per changing transaction; `(commitVersion,eventIndex)` orders its events. Epochs increase independently of entity versions; events record the epoch. A no-op command records a receipt if needed but does not create a fake entity transition. Evidence-only commits can advance the global cursor without changing displayed entities. A store restored to an older backup must receive a new lineage and explicit recovery; it cannot advertise lower versions under the old lineage.

Transaction sequence: validate frame/size; authenticate; first look up the command receipt under the original stable issuer and immutable request digest (section 7.1); only for a previously unaccepted request validate live fencing/preconditions and admit bounded work; retain accepted request bytes; apply allowed transitions or prepare a bounded immutable change; write exact evidence, command receipt, outbox and event batch; durable commit; publish the immutable new read model and receipt. Admission/rejection receipt is distinct from authority-change commit and application settlement. Failed validation is `not_accepted`; an accepted durable command remains queryable even if prepare, dispatch or reply fails. If durable storage cannot accept bytes, reject admission explicitly; never claim success then lose an in-memory queue.

Durability requires WAL and full commit synchronization on supported local storage, with crash/reopen fault fixtures for the actual chosen SQLite/runtime build. Hardware failure, disk loss or dishonest fsync is outside ordinary process-crash proof; verified independent backups remain necessary. No distributed transaction across legacy databases is claimed. During strangling, the new transaction commits an outbox intent; legacy projection delivery is a separately replayable step and is reported as pending until verified.

## 5. State machines and execution evidence

Allowed transitions are validated by the broker; clients propose commands/observations, not replacement entity documents. Lifecycle, connection, progress, supervision and executor freshness are orthogonal fields so one label cannot hide an unresolved condition.

| Entity | Allowed lifecycle/transition contract |
| --- | --- |
| Session | `registered -> connected -> disconnected -> connected`; explicit `ended` retires a registration/session role. Authenticated reconnect increments registration generation without changing stable logical session ID. Busy/idle/unknown activity is a versioned observation separate from connection and ended state. |
| Job/current turn | `requested -> queued -> starting -> running -> finishing -> terminal`; `starting -> start_failed`; `requested/queued -> terminal(cancelled_before_start)` only by authorized exact-turn command. Running can enter `stopping` on accepted cancellation, then `finishing -> terminal(cancelled)`. `interrupted` records acknowledged interruption; `evidence_unknown` is an execution-evidence field, not automatic death. A terminal job can receive an authorized continuation that allocates a new generation and returns to `requested/queued`. `start_failed` is terminal for that generation and keeps its failure receipt. |
| Run/executor | `allocated -> admission_pending -> launch_intent -> launch_acknowledged -> executing -> finishing -> exited`; `launch_intent -> start_failed` requires failure proof. Connection lost sets evidence `unknown`, retaining last lifecycle. Recovery must resolve the launch/executor attachment before retrying. Run exit, result retention and report delivery are distinct facts. |
| Message | `accepted -> routed -> delivered_to_transport -> handed_out -> consumed` where receipts exist; `delivery_unconfirmed` is retryable under the same UUID. Withdrawal/reroute retains original routes and consumed proof. No claim that transport acceptance or hook hand-out means model display. |
| Approval | `pending -> answered(allow/deny)` or `expired/cancelled`; exact terms/version/run required for answer. Answer receipt is distinct from executor application acknowledgement. Reconnect never applies permission to a newer generation. |
| Owner question | `open -> answered/cancelled/superseded`; answer is immutable intent under version/replay checks. Delivery/mirror states remain independently retryable. Default-answer behavior retains existing authorization exclusions; no timeout substitutes for required owner approval. |

All terminal outcomes are immutable for their exact generation. Completion from an earlier generation is retained as evidence and cannot finish a new turn. Progress may be coalesced before command admission; a committed progress command is not discarded from evidence. Finishing means the same executor is settling and retaining results; it is never exposed as ready for a new executor until settlement is committed. Typed refusal reasons distinguish transition contention, cancellation, interrupted/unknown executor, unsettled runner and stale generation, instead of ambiguous `stopping`.

An executor must receive durable result/evidence acknowledgement before declaring its report complete or intentionally exiting. While the daemon is unavailable, bounded volatile retransmission retains the same report UUID and applies backpressure; no success is claimed. Native CLI transcripts may provide separately retained external evidence on reconnect. Simultaneous daemon/executor failure before a result was accepted can leave execution evidence unknown; this design does not invent client-owned durable spools or promise recovery of bytes never durably accepted anywhere. The acceptance fixtures distinguish accepted-byte preservation from unacknowledged external execution output.

Execution evidence is `not_started`, `launch_pending`, `confirmed_active`, `confirmed_terminal`, or `unknown`, carrying exact generation, executor instance and last observation/version. Heartbeat expiry produces unknown/degraded evidence, not automatic cancellation or another process launch. A PID can be reused; process creation identity/native binding corroborates an authenticated executor but is not a substitute for it. Null native session/workdir is permitted during admission. A legacy label-only record imports as unknown historical evidence until an authenticated existing executor/receipt reconciles it.

Recovery is identity/turn reconciliation, never duplicate-job creation. A replacement relation is an explicit retained `supersedes/supersededBy` link with provenance and authorization; display collapse does not cancel either execution. AB-324's never-started/replaced report would remain visible as an unresolved legacy record until proved. A recovered `running` word cannot occupy an admission slot as proven execution, and lack of a holder cannot free a reservation without the defined settlement/reconciliation rule.

## 6. Session identity, handoff, rename and reports

Use separate broker-issued IDs for logical session, current registration, native thread, immediate parent job, root supervising session and concurrency root. A binding is established on an authenticated connection/capability challenge or explicitly authorized recovery with corroborated retained identity. A caller supplying another session's string or a matching project path does not acquire that identity. Project-main is a distinct versioned role; changing it does not silently change job supervision. Name normalization or stripping `-2` is never identity proof.

Rename changes the display/canonical name and alias lookup inside a session transaction. Job owner IDs and permissions stay bound to the same authenticated identity; reports, controls, projectJobs and dashboard agree on that identity. Reconnect to the same proven session changes registration generation. A new native session in the same project receives an explicit bind/handoff command and receipt; no forced project-wide ownership. A name reused by a different session gains no control or retained mail.

Handoff transaction requires exact selected jobs/current versions, authenticated source rights and target live registration generation. It changes immediate supervision only for root jobs, root lineage for descendants, explicit grant substitutions and routing revision together; nested children keep their immediate parent job. It preserves original project/run creation context, all historical masters/ownership changes and active execution. An all-jobs operation selects at a documented version and fails stale preconditions if membership changes. Section 7.2 selects an immutable manifest/pointer activation mechanism with concrete provisional tree/byte ceilings; owner choice 4 ratifies measured sizing, not whether partial supervision is allowed. Section 3.1's application barrier must settle affected permits before grant changes activate.

The transaction inserts ownership events and delivery/child-refresh outbox entries. A receipt distinguishes `authority_committed`, `host_attached`, `child_metadata_acknowledged` and `control_consumed`; a moved-row count proves only the first. Update the active child's authenticated ParentLink/ParentClient metadata with current supervisor IDs/name, routing revision, turn and grants; refresh before MCP `send` classification, peers descriptions, escalation and progress. Literal `parent` resolves server-side current immediate supervisor. Keep the same link/token/child and exact grants; an unavailable/stale link returns a typed unconfirmed/refreshed-metadata requirement, never a sibling reclassification based on the original name. Test the actual MCP handler, not only `ParentClient.send`.

Report transaction retains exact result bytes/digest, job+generation/run, report UUID and executor observation. It computes the **current** primary recipient by stable identity under the same transaction as route/outbox insertion. Handoff and completion racing serialize in the writer: if report commits first, handoff reroutes only pending unconsumed delivery; if handoff commits first, report targets the new supervisor. Consumed messages are not replayed to manufacture a new report. If the primary is offline, retain its mail and expose pending delivery; existing authorized fallback policies may create an explicitly identified route/copy, without conferring control on that fallback. On reconnect the primary resumes its exact consumption history.

### 6.1 Stage-2 job mail includes consumption authority

Move the **job-report/question routing, hand-out and consumption subdomain with jobs**, not only the outbox. This includes exact job-derived primary/fallback envelopes, their pending routes, consumption and retraction; delivery/ACK paths through hooks, `inbox` (including mark-read), `send(reply_to)`, node/local read journals, native-child ACK where relevant, wake/rewake hand-out, broker `ack/markRead`, durable replay and maintenance/doctor overlays. Stage-2 promotion requires every writer or consuming reader capable of touching those IDs to submit commands to this subdomain. Unknown legacy hooks or direct read-journal writers defer promotion of the affected job-mail authority; a broker outbox alone is insufficient. Stage 4b still migrates general session/sibling messages and remaining message domains.

Under a drained writer/reader barrier, import all applicable original envelopes and route/consumption receipts from live/archive/overlay/read-state sources into state core. Preserve conflicting receipts as evidence and mark ambiguous delivery unknown; no last-timestamp guess authorizes replay. Current job-mail bodies and delivery decisions reside in core after cutover. No new report is published into a writable legacy inbox/journal as a second consumption authority. Legacy-compatible RPC can serve the core row; a hardcoded old inbox consumer cannot participate and blocks the relevant promotion. Other domains still in legacy mode retain their independent operation without writing core-owned job-mail IDs.

Each consuming hand-out atomically obtains `delivery_claim(messageId,routeRevision,recipientSession,registrationGeneration,claimId)` in core and marks the envelope handed out/consumed at Bridge's existing hand-out boundary **before** returning content. Claim IDs deduplicate retries; consumption is global for that envelope's delivery intent, with original recipient/registration proof retained. A claim is never released for rerouting merely because transport/display ACK is absent; that would replay an already handed-out message. A response lost after commit is delivery-unconfirmed/display-unknown and queryable, not proof the model read it. Non-consuming peeks do not acquire a claim. Native model-display acknowledgement, if later added, is a different fact and does not redefine existing consumption.

Consumption and handoff therefore serialize in one writer: (a) claim/consumption commits first, so handoff retains the consumed route and creates no new deliverable copy; (b) handoff commits first, so it changes only an unclaimed pending route/revision and a stale old-recipient claim fails without content; (c) a claim was committed but its reply/channel is unsettled, so handoff cannot reissue the envelope to another recipient. Consumer reattachment/receipt lookup can recover the same claim; no fresh claim or message UUID retries the effect. During manifest prepare, any claim/ACK/route change increments the delivery dependency revision and invalidates the entire prepared handoff.

At the **legacy-to-core cutover boundary**, drain all legacy hand-out/ACK paths and checkpoint their journals before preparing the import. Crash after legacy delivery/consumption but before its checkpoint/import requires reconciliation from retained authoritative receipts or the capable original consumer; affected routes remain `delivery_unknown` and promotion/replay stays blocked until proved. A missing receipt or timeout cannot mean unconsumed. Crash after core claim/consumption commit but before reply/ACK preserves the core receipt, so restart/handoff never redelivers; crash before any claim commits leaves the envelope pending. No distributed atomic legacy/core delivery is asserted: legacy in-flight work must be settled by the barrier, and all post-promotion consumption is core-only. Rollback after promotion keeps this subdomain and receipts in a compatible daemon; it cannot resume legacy ACK writers.

Ordinary mail to a job stays unsupported and must return `not_stored`. `message_subagent`/job control, granted sibling messaging and project-main messages remain distinct operations with existing depth/slot/hop/ownership/permission guards. UI/mobile commands carry exact job ID/generation/version and are reauthorized immediately before dispatch. A read-only authority timeout means no control was submitted, and at most the existing bounded read retry applies; it is not permission to retry mutating controls without a command receipt.

## 7. Immutable snapshot and ordered delta protocol

Handshake negotiates protocol version and per-domain read/command/event capabilities. Command frame separates mutable connection fencing from immutable request identity: `{transport:{installationId,lineage,brokerEpoch,registrationGeneration,channelNonce},request:{commandId,operation,entityId,expectedVersion,jobGeneration?,expectedTargetRegistration?,grantRevision?,payload}}`. The stable issuer/binding is derived by server authentication; it is not trusted as an input identity. Canonical **request** bytes, including logical expected-state/grant/target preconditions, define the digest and are retained exactly; original transport bytes are also retained as evidence but are excluded from deduplication identity. Return typed conflict/unsupported/backpressure/durability/unconfirmed errors, receipt status and current safe version hints. Section 7.1 specifies lookup order and reconnect rights.

### 7.1 Lost replies, receipt rights and reconnect order

Receipt key is `(installationId,lineage,stableAuthenticatedIssuer,commandId)`; request digest covers the immutable request only. A fresh authenticated connection may update transport epoch/registration/channel metadata without changing that key or request. Before testing old entity/grant/target preconditions, the daemon authenticates **receipt access** and looks up this key: identical recorded request returns its committed/pending/failed/application-unknown receipt without executing again, even if the requesting registration or broker epoch changed. A different request digest conflicts and is retained/rejected; changing an expected entity/grant/target precondition under the same ID is not a retry. Only an unaccepted request goes through current transport epoch, exact entity/turn/target/grant validation and effect admission. Revoked/bad current transport authentication cannot bypass security via receipt lookup.

`commandReceipt(commandId,requestDigest?)` is a read-only authenticated operation over the original issuer's ledger. A proved reconnect to that **same** stable issuer receives a narrowly scoped receipt-query capability from the daemon; native thread string, same project, name reuse, new supervisor role or an arbitrary old credential cannot confer it. Credential rotation requires current authenticated binding/recovery proof; revoked issuer capabilities require explicit authorized recovery, not automatic inheritance. Receipt access never restores control/grants or submits outbox/native effects. If the current principal cannot read original private payload/result, return only its authorized receipt status/digest or refuse; do not leak another issuer's evidence.

After reply loss/epoch change the client performs current handshake, then this receipt query. `accepted/pending`, `authority_committed`, `application_unknown`, `applied`, and retained failure are distinct outcomes; an unresolved outcome never permits a replacement command ID. `not_accepted` is definitive only after the daemon has recovered the applicable ledger and serialized lookup with outstanding acceptance; otherwise return `receipt_unavailable/unknown`. An identical immutable request may be retried under its original ID on a fresh transport if definitively absent, subject to unchanged logical preconditions and full current validation. Lost-reply recovery never resubmits the effect under a fresh ID. New intent after a proved rejection/conflict requires a deliberate authorized command with fresh state, not an automatic retry. Store-lineage change requires reviewed recovery/receipt reconciliation; absence in a new lineage is not proof an old effect never happened.

### 7.2 Atomic change manifests and bounded fragments

Chosen correctness mechanism: a logical transaction/event batch may reference **one immutable verified manifest**, rather than fitting all logical events into a single wire frame. Provisional pre-admission ceilings are 8 MiB of canonical activation/event material, at most 1,024 selected jobs and 4,096 affected pending job-mail routes, at most 96 KiB fragment payload in each 128-KiB wire frame, at most two pending prepares/16 MiB aggregate preparation bytes in the daemon, and at most 8 MiB staging for one transaction per reader. These sizes require owner choice 4/CI ratification; all-or-none activation/reader application is mandatory regardless of sizing. Larger requests fail typed `change_too_large` before authority mutation; `all` is not silently split into partial handoffs. Existing 256-KiB command frames may stage evidence by immutable blob reference; neither accepted command bytes nor oversized evidence are truncated into events.

Preparation records are written by the broker in bounded low-priority batches and are **not current state**. Manifest lists ordered fragments, SHA-256 digest/byte length per fragment, total digest/length/event count, exact selected job membership and previous/new entity/grant versions, source root/tree membership revision, job-mail route/consumption revision, grant-policy revision, target registration and required settled-application barrier revision. All writes that can invalidate the selection or expected versions bump the corresponding broker-owned dependency revisions, including job create/attach/continue, ownership/grants, ACK/claims and registration/revocation. Preparation uses a captured snapshot; unknown dependency writers prohibit promotion. Prepared effective rows/index deltas/events are retained immutable bytes; schema/current-view joins consult them only after activation.

Final sole-writer transaction CAS-validates those dependency revisions, issuer rights, epoch and settled application barrier, then atomically selects the prepared effective rows via a manifest activation pointer, allocates one commit version and appends one activation/event header plus manifest reference, command receipt and bounded outbox-dispatch references. If any dependency changed or bytes/size verification fails, the entire activation rejects; old authority remains selected and rejected preparation/evidence stays retained. Every state query/control/snapshot uses the same effective-current view/pointer, including its prepared count/order/group/index deltas, never background-materialized rows alone. Prepared new entity versions become current only with that commit header; general queries join the overlay using indexed entity/membership keys. Post-activation materialization is an optional projection and cannot create a second commit/owner change. There is no unbounded per-job rewrite in the final control transaction; prepare/query latency and indexed overlay cost still require measurement.

Wire protocol sends an activation header `{commitVersion,manifestId,manifestDigest,totalBytes,eventCount,fragmentCount,filterRevision}` then bounded fragments scoped to reader authorization; the scoped manifest has its own verified digest/count and does not expose unauthorized references. ACK/frame credit lets fragments drain without keeping the whole batch in the 1-MiB network queue. Reader verifies fragment order/index/digests, totals, previous entity versions and dependency on its prior cursor, constructs a replacement immutable model in bounded staging, then verifies a matching commit-end header. Only then does it swap state and advance **one** cursor for the entire transaction. Missing/duplicate-conflicting fragments or authorization/epoch change discard staging and require exact replay/resnapshot; no fragment independently advances authority or badges. Until full verification readers retain the old committed model.

Backpressure abandons transient staging, not durable prepared/event bytes. Snapshot transfer uses the same verified chunk protocol and all-or-none model replacement. If an authorized reader cannot admit the advertised logical transaction/snapshot size, negotiate a bounded page/reference-capable projection before subscription or return `read_capability_unavailable`; do not send an impossible batch followed by endless automatic resnapshots. Snapshot selection tokens reference immutable material, not a live SQLite transaction. The 8-MiB staging ceiling is per complete state projection/activation material in the baseline; larger installations need an explicitly paged immutable reference model, not weakened atomicity. These bounds are finite workload assumptions retained for owner sizing review.

### 7.3 Snapshot capture, application and backpressure

Snapshot envelope: `{installationId, lineage, epoch, schema, commitVersion:N, subscriptionScope, filterRevision, sessions, jobs, currentTurns, counts, orderKeys, availability, evidenceCursors}`. Read all state at one committed SQLite snapshot and copy/serialize it immutably; never expose mutable manager maps. Derived counts/order/group ownership are produced from the same transaction/read-model version. Transport `sampledAt`/health timestamps live outside the state payload; unchanged state payloads are byte-identical after canonical serialization, including stable key ordering. Pages share a snapshot token; expiry returns `snapshot_required`, never mixed pages at newer versions.

Subscribe atomically at N: capture the snapshot watermark and install/replay the subscription from the committed event log without a capture/subscribe race. Delta batches contain `{fromExclusive:N, toInclusive:M, epoch, lineage, filterRevision, complete:true, events:[{commitVersion,eventIndex,entityId,previousVersion,version,kind,payload}]}` when bounded inline; otherwise section 7.2's verified activation manifest represents the same complete logical batch. `complete:true` applies only after matching commit-end/verification, not on an arbitrary fragment. Commit batches are indivisible to readers; client applies to a new immutable model then swaps the whole model. Scope-filtered streams include cursor-advance batches for commits with no visible events, so an absent entity event is not mistaken for a gap. Authorization/filter changes force a new scoped snapshot; no data outside rights is leaked by replay.

Accept duplicate already-applied batches idempotently; reject entity version mismatch, missing batch range, changed lineage, incompatible epoch or truncated transaction. Epoch change triggers a handshake and snapshot even if the durable sequence remains continuous. A client never repairs an authority gap by merging old run pages, querying files or guessing status. History pages carry immutable evidence IDs and their own cursor and cannot overwrite current entities. Tools needing current control rights query broker authority, not a presentation cache.

Bounded delivery: initial proposal is 128 KiB per delta frame, 256 frames/1 MiB queued per subscriber (whichever first), and a 32 MiB shared replay cache, with section 7.2's separate 8-MiB atomic staging/credit protocol. Client ACKs cursor after full application, and ACKs frame credit without advancing its logical cursor. At overflow, retain durable state/events, stop incremental enqueueing, mark this subscriber `resnapshot_required` and offer the latest capability-compatible bounded snapshot. This is flow control, not reader eviction or a global version floor. Persisted events remain retained; an old reader can resume by paged replay or snapshot without forcing any other reader to advance. Snapshot chunks also have byte/time/concurrency admission; an indefinitely stalled reader cannot hold a live SQLite read transaction or WAL growth hostage. Serialize bounded pages from a materialized retained snapshot, releasing the live read transaction promptly.

Remote PCs have independent installation authorities. A combined dashboard carries a vector of per-host snapshot/epoch versions and availability; there is no invented globally atomic cross-PC commit. Each host's rows are internally consistent. Stale/unavailable remote state is labeled and cannot authorize local control. Desktop, mobile and tools for the same host use the same read model and event vocabulary, with permissions controlling field projection.

## 8. Presentation contract

Stable order keys use PC identity, durable project identity/order key, session creation order and immutable session ID tie-breaker. Project labels, running counts, activity, progress and last-event time do not change default order. Explicit user sorting is a separate presentation preference. Renames do not move default rows. Parent/child grouping uses IDs from the same snapshot; the same job appears once even with many runs, aliases or older history pages.

Expose exact counts for requested/queued/starting, working, finishing, stopping and unknown/degraded execution. The working badge counts unique logical jobs whose **current generation** is `running` with confirmed active executor evidence. Finishing/stopping remain visible active work in distinct counts; unknown is visibly unresolved, never a silent zero or a proven working badge. Do not count historical `running`, stale heartbeat or imported label-only records. With no accepted changes counts/order/state are unchanged across repeated snapshots.

Ended means a disconnected/ended session row, not that its jobs ended. Retain genuinely detached active/current jobs under their authoritative supervising identity (with ended supervisor shown) and surface unresolved orphans. Collapse terminal historical rows by default; expand/paginate preserved history without deletion. Changing a grouping/display preference never settles a job or frees capacity.

If busy/idle flicker still needs presentation hysteresis, use named constants (proposal `DISPLAY_BUSY_HOLD_MS=1500`, `DISPLAY_IDLE_CONFIRM_MS=750`) in existing render adapters only, with raw versioned activity exposed for inspection. Terminal/current job badges and authority counts are not delayed. Hysteresis does not affect actual wake scheduling, slot admission, cancellation, permissions, handoff eligibility or broker state. This extends existing UI components; no UI rebuild or creative redesign is in scope.

## 9. Scheduling, query complexity and latency budgets

Daemon RPC loop prioritizes ping/health/readiness, authenticated send, exact jobAuthority and handoff/control admission. The sole writer has bounded priority mailboxes, with fair per-principal queues; a continuous hostile control flood cannot starve committed bulk/projection work forever. Low-priority imports/aggregation/index/projection are admitted only in small batches; parsing/compression/hashing/native transcript reads run in workers. Workers send candidate bytes plus source/version witnesses, never writable SQL handles. After yielding/worker completion, recheck authority/versions before accepting results.

Initial sizing to measure: command frame at most 256 KiB, at most 256 queued control commands/8 MiB total, at most 16 in-flight per principal, 64-record/256-KiB bulk commit batches and a 2-ms target writer slice excluding storage commit. Admission limits preserve existing public payload limits via explicit chunked evidence upload if necessary; never truncate accepted bytes. Separate memory budget for snapshot materialization (two active snapshots, 8 MiB each in the baseline fixture). Health does not queue behind bulk; health must expose writer queue age, commit lag, stalled domains and outbox lag so a fast RPC loop cannot conceal a dead writer. These are proposed parameters, not measured guarantees.

Disk-full/unavailable state denies new mutation safely while surfacing retained state/health. Never achieve responsiveness by dropping detail/history, disabling guards, forcing readers out, deleting data or reporting stale authority as fresh.

## 10. Strangler migration, skew and rollback

Use two independent durable pointers, never one combined mode:

| Pointer | Legal states/transitions | Selected authority / rollback |
| --- | --- | --- |
| `domain_modes.target` | `legacy_selected -> shadow -> prepared -> authoritative`; pre-promotion `prepared -> shadow` or `shadow/prepared -> legacy_selected` may reject/disable preparation without deleting it. | Legacy remains current in legacy_selected/shadow/prepared. The promotion transaction atomically changes the authority selector to core; `authoritative` remains the target state thereafter. Compatible daemon rollback keeps core selected. Recovery/unavailable is a separate availability flag, never fallback to legacy. |
| `legacy_source_modes` per domain/source generation | `live_external -> quiescing -> retained_read_only`; verified captured snapshots may be retained_read_only while their origin is still live for unrelated domains. A resumed/conflicting external writer produces a new `conflicting_external` generation, never promotion of that evidence to authority. | These states describe source/import/preservation, not the current writer. Rollback never changes a retained source to live/current after core promotion. Every original/import generation remains retained. |

Cutover receipt records both selector and source generations/manifests. Shadow/prepared bytes never feed permissions, badges or controls. The end state is one store/single writer; step 1 is explicitly a process extraction with legacy writers temporarily intact and cannot claim this end state. A shared legacy database can still host unmigrated domains; imported generation snapshots and migrated-domain original rows stay preserved, while permitted unrelated writes are tracked as new source generations. No physical file-wide read-only/deletion step is falsely required while other domains use it. Every promoted domain's writers and consumption/admission paths must close independently.

1. Inventory source generation and every capable/legacy writer for the domain, including detached/inline/native/remote hosts and doctor/archive utilities. Capability closure is based on registered authenticated behavior plus conservative known legacy capability rules, not a release string alone. Unknown executable identity or unsatisfied file/DB admission blocks domain promotion; it does not evict a reader or terminate a process.
2. Broker requests a domain write-admission barrier from capable writers and obtains their drained checkpoint/accepted-command receipts. Unknown legacy writers cannot be fenced by the new RPC protocol. If they can still execute/overwrite the same logical domain, defer its cutover until owner-controlled compatible transition or their voluntary exit. Old read-only consumers may remain indefinitely. Do not pretend an arbitrary old direct file writer can be remotely fenced.
3. Use SQLite consistent read-only snapshot/backup or verified immutable file copy, hash/count/length/manifest and physical containment. Preserve WAL-consistent content and full unknown tables/columns/fields/raw JSON occurrences. Import chunks idempotently by source identity+generation+digest, retain conflicting records separately, then verify source witness again. A changed source creates another retained generation; it is not called a completed one-time import. Stable generation imports exactly once.
4. Reconcile current state only from authenticated exact executor/turn, confirmed receipts and authorized identity mappings. Legacy `startedAt` maps to a retained legacy turn key, not a new generation permission. Ambiguous IDs, owners, launch or completion stay unknown and block affected controls. Preserve source and accepted bytes even if they cannot be projected into current typed tables.
5. Prepare cutover manifest, verify retention/coverage and same-source replay, then transactionally promote the target authority selector, current state, event checkpoint and authority fence. Switch capable writers to commands. Compatibility adapters project old read protocols without becoming another owner. Move captured legacy source generations to retained_read_only and stop all writes to that domain's original rows/files; preserve whole consistent snapshots where other legacy domains share a physical database. Unrelated unmigrated-domain writes do not select legacy authority for the promoted domain. No client-enforced permission change or source deletion is part of this transition.
6. Old reader requests are translated by daemon protocol adapters if representable. Unsupported authority operations fail closed with upgrade-required/domain detail; do not silently accept an old command or turn a current state into a guessed legacy status. If an old reader hardcodes a file/DB path, its retained original remains readable historical evidence and may be stale; no claim of fresh authority on that path. A separately negotiated broker-written export may support it without overwriting originals, but must be reviewed before adoption.

An unknown/newly launched old writer after promotion cannot write `state-core.db` through supported APIs. Its old-file bytes are evidence only; detect conflicting source generations and expose unsupported-writer state. Preventing it from launching duplicate legacy executors requires the cutover's writer/admission closure and deployment constraints; if that cannot be established, the domain must not promote. No claim of safety against arbitrary same-user software bypassing the protocol. No global reader floor or forced shutdown is a substitute for this proof.

After authority promotion, restoring old stores as writable current state is **not** ordinary rollback. It would discard post-cutover authority or create two writers. A downgrade requires a separately reviewed lossless export/reconciliation and writer barrier, preserving new store/events/receipts and all originals; otherwise refuse unsupported downgrade while keeping a compatible daemon serving. An old executable opening an incompatible new schema fails closed. Reader capability skew can select older projections without changing the current writer mode.

AB-228/215 protections apply independently to import, backup, pending receipts, conflict containment, source preservation and upgrade/finalize paths. No source deletion, absorption/finalize, reader-floor raise or retention proof bypass is added here. Retention means searchable archive/evidence references; all raw accepted bytes remain retrievable under authorized access. Bounded memory/replay windows do not bound or delete durable history. Finite disk capacity is explicit: stop admission before loss and request operator capacity, never promise infinite preservation on finite storage.
