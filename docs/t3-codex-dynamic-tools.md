## Verdict and trust boundary

Codex already implements a private native request/response primitive sufficient to distinguish root and child calls for an app-owned Bridge messaging adapter. T3 can register non-secret tool schemas at native `thread/start`, receive `item/tool/call` over its owned app-server stdio, compare native thread/turn IDs to its active root mapping, and return a result only through that request's response path. No new Bridge token, T3 MCP bearer, provider shell environment, or orchestration capability is needed. Tool names, schemas, arguments and results are provider-visible; broker credentials and registration ownership stay with T3.

**This conclusion requires the private child-process stdio boundary.** It does not apply to a shared TCP/WebSocket app-server: normal dynamic callbacks are not bound to an exclusive connection owner. The patch's optional port must stay absent for an unverified runtime or transport. Source support is sufficient to prepare the adapter; enabling it requires upstream compile/transport and native acceptance.

This route addresses new Bridge tools only. Existing T3 MCP configuration and the separate problem of native children borrowing its existing orchestration credential are unchanged. The package does not close AB-458 native acceptance or claim that all native T3 tools are now child-isolated.

## Smallest exact follow-on package

Artifact directory: `E:/AgentData/reports/ab458-dynamic-tools-20261022-t32af0942b`.

`t3-codex-dynamic-bridge.patch` applies against T3 `968dd51704441138559a3fe9c348719f2b11e0c6` and changes only:

1. `apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts`: optional app-owned port factory (absent by default), scoped finalizer, method-specific request handler and raw experimental start registration. No composition site provides the factory in this artifact.
2. `apps/server/src/orchestration-v2/Adapters/CodexBridgeDynamicTools.ts`: immutable app/provider/session/root lease, synchronous one-start reservation, live root/turn checks, Bridge main-lineage admission hook, bounded replay refusal, abort/revocation checks, sanitized failure, and five explicit port methods.
3. `apps/server/src/orchestration-v2/Adapters/CodexBridgeDynamicTools.test.ts`: focused mocked registration/dispatch fixtures importing T3's actual generated protocol/RPC types. No hand-authored replacement protocol interfaces.

The namespace is `agent_bridge` with `peers`, `pending`, `read_message`, `send`, `send_status`. Exact argument whitelists reject scope/native identity/frontend overrides and generic opcodes. The provider cannot register a broker identity, spawn work, delegate, control tasks or invoke arbitrary Bridge MCP handlers. The real app port must preserve Bridge `codexMainThreadAdmission` (`src/mcp/codex-lineage.ts:94-112`) using the now-trusted native ID. Passing the private channel check must not bypass lineage, ownership, depth or hop rules.

The broker connection and its opaque registration generation belong to the injected app port. Every effect must check the same captured lease and live guard at its actual acceptance boundary. Peer references must be app-scoped and resolve to pinned authorized destinations; durable sends/read acknowledgment/status retain Bridge semantics. Do not wrap the full existing MCP `send` handler, which also has task/job-follow-up paths. Wakes or task actions, if approved later, remain host callbacks through the already-scoped T3 services described in the previous contract; they are absent from this provider toolkit.

A root binds only from the response to this session's reserved `thread/start`. The artifact deliberately does not rebind from `thread/resume`, persisted definitions or tool arguments. A resumed root in the same still-live session may retain its original binding; a new session denies persisted tool calls. Revoke/close aborts the old handle, never transfers pending work or results to a replacement, and never retries an uncertain send. The replay set refuses further calls after 1,024 unique accepted call keys in one session; there is no silent eviction. This conservative prototype limit needs an explicit production policy.

## Remaining implementation prerequisites

The required Codex primitive exists at the inspected pin for private stdio; **no new Codex protocol feature is required for this bounded route**. Upstream T3 changes are unavoidable: it currently registers neither these dynamic tools nor their handler. Parent review must precede integration.

Before any enablement:

1. Compile the exact patch in the pinned T3 workspace and run a focused mocked adapter/client replay test through the real Effect codecs and private transport. Verify experimental registration and root/child response routing against an owner-approved compatible Codex runtime. This research intentionally did not probe or upgrade the installed runtime.
2. Implement/review an app-owned Bridge messaging port and composition/lifecycle owner. Preserve broker authentication, frontend/host-lifetime checks, main-lineage admission, atomic lease admission, destination ownership, durable receipts and scoped revocation. `BridgeNode`'s CLI-parent-PID derivation is not an app integration API; see the previous contract. The artifact supplies interfaces and fixtures, not that production connector.
3. Choose a reviewed durable root-restoration policy before restart/resume support. Do not infer ownership from persisted dynamic schemas. Existing threads without schemas need a new native root; do not invent an unsupported resume registration field.
4. Prove native root success, inherited child refusal, wrong-turn/unknown refusal, two app scopes, revocation during admission/submission, and replacement non-retargeting with the real connector. Keep the optional port absent until these gates pass. Existing native T3 MCP child isolation remains a separate unresolved boundary.

If private stdio ownership or origin routing cannot be retained, disable the adapter and return the exact transport gap upstream. Do not fall back to unsigned HTTP identity or credential injection.
