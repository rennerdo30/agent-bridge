# Cross-PC T3 messaging acceptance (AB-458)

Current source contract: local protocol **5**, mailbox schema **13**, paired-host `recipientOwnershipV1`, `nativeOwnershipV1` and `mailboxProvenanceV1`. Protocols 3/4 and schemas 11/12 below describe intermediate, unreleased branch states, not shipped versions. Pairing version is unchanged. Parent approved the round-five compatibility gates; no installed update or migration launch is part of this work.

Exact recipient ownership fences delivery, claims, inbox reads, ACK/recovery and retargeting. Existing authenticated shared archive access is separately authorized: `searchHistory`, `getConversation` and the existing archive/dashboard readers can expose mailbox-derived bodies. This package does not provide confidential per-recipient storage, end-to-end confidentiality or full data isolation. Parent explicitly retained that archive contract; AB-459 records a separate owner decision about private mailbox-derived history.

## Scope and observed defects

Base: `70820a0fd090bd12f8245e9cf7e51db13a78eef0` (`main`). This package changes paired-PC message routing, with no remote task protocol, installed update, provider launch or live other-PC traffic.

On the base, `src/network/link.ts` stripped `PeerInfo.frontend` from peer advertisements. Send frames identified the destination only by its name. A stale advertised name could therefore reach another T3 thread or an ordinary native session without comparing the destination's attested binding. A focused loopback fixture reproduced missing frontend metadata and accepted stale thread/scope/provider/native/missing destinations.

Checking the exact name at network ingress alone was insufficient: `Broker.receiveRemote` also resolves retained aliases. A separate failing fixture showed that an unfenced alias reached a hosted target. The broker now checks the fence again after resolving that alias.

## Implemented routing contract

1. Each local T3 MCP session already attests its frontend to its local T3 host. The network advertises only the validated non-secret binding: `kind`, endpoint scope digest, `threadId`, and `providerInstanceId`. Provider-native `sessionId` remains separate.
2. Separate hello features `t3ThreadRouting`, `recipientOwnershipV1` and `nativeOwnershipV1` negotiate thread fencing and exact ownership. They do not consume slots in the existing bounded extension arrays. Missing ownership negotiation refuses send/receipt requests in both directions before mailbox effects or receipt release. Advertised native-to-native traffic can operate without T3 routing only when the native identity capability and exact fence are present. No bearer credentials are added.
3. Before the first wire attempt, the broker commits the original request owner/content and destination intent. The latter includes authenticated host ID/fingerprint, exact target and either complete frontend or typed native owner. It excludes the replaceable registration ID. Retry compares the immutable owner with current authenticated advertisements and refuses changed host, thread, provider, native session or process incarnation. The negotiated frame carries `destination: {peerId, frontend?, native?}` and authenticated sender ownership. The current matching registration ID fences only that wire attempt. Source ownership is also retained for duplicate/receipt authorization.
4. Both network and broker ingress compare the exact name, current registration fence and complete durable owner before storage/emission, including retained aliases. A missing native identity or destination refuses; absence of a frontend field is never native authority. A caller must deliberately select a new destination with a new operation identity after inspecting the refusal; automatic retry preserves the original intent.
5. Normal TLS-PSK pairing and advertised-sender authentication remain authoritative. Neither the sender's nor the destination's T3 endpoint URL or authorization grant travels over the paired-PC link. The binding is a routing fence, not a bearer credential.
6. The destination's existing local `T3Waker` submits a pointer to unread Bridge mail through its locally scoped `T3Host.send`. It targets the attested destination thread, never a provider-native session ID. A wrong-thread receipt is an unknown outcome. Refused/unknown wakes leave mail unread and do not fall back to native CLI wake or automatically replay an admitted operation.
7. Each hosted recipient copy persists `recipientFrontend` ownership. Pending reads, deferred hello replay, reply-conflict reads, queue claims, acknowledgements and duplicate receipts must match that ownership. Registration IDs may change; the full scope/thread/provider binding must match. If another live session occupies the former name, the original frontend can reclaim only its owned copies into its newly assigned name. Broadcast copies remain independent. Unmatched copies stay stored. An unfenced legacy message is ambiguous and cannot be claimed or acknowledged by any native or hosted successor. New native copies require explicit registration provenance. Internal fresh notifications bind their selected live or verified offline recipient; recovered envelopes retain their original ownership rather than being reattributed from a reused name. Existing authorized supervisor transfers explicitly bind the new copy; name-only read journals do not acknowledge hosted mail.
8. Message IDs retain the existing content checks and dedupe rules. Reconnect replay recovers the stored receipt without duplicate mail. Source send-state/retry/receipt access checks the retained sender intent, and remote receipt queries cannot switch to a different host with a reused display name. The persisted local wake journal suppresses duplicate wakes across waker reloads, including refused/unknown outcomes. Inbox consumption remains separate from storage and wake acceptance.

## Schema migration and compatibility

Schema 12 introduced authoritative `owner` and `sender` fields and typed native offline registration evidence. Schema 13 adds separate per-copy `mailbox` and `source` provenance, namespace fields for send intents, remote pins and job delivery routes, and a singleton `mailbox_store` namespace. It does not rewrite any original message/archive rows, proof strings, ownership columns, intent payloads, read timestamps or journals. Namespace creation and all additive columns share the existing transactional migration/snapshot boundary. Shipping-base-to-13, intermediate-11-to-13 and intermediate-12-to-13 are covered; interruption rolls back, and repeated admission preserves the same namespace.

A complete hosted binding proves an owner, but an intermediate row without recorded direction cannot prove that it was a local mailbox copy: an earlier remote copy may already have been claimed under a local name. All such original rows retain their proof columns and contents with empty new provenance and remain quarantined, including typed schema-12 native rows and schema-10 hosted rows. A display address, matching native ID, current advertisement or missing pin cannot repair that evidence. Schema-11 native strings also remain untyped evidence; no string is guessed into session/process provenance. Old namespace-less read marks and send/route records are retained without new consumption, retry or settlement authority. Newly captured verified offline registrations and authorized local durable job records can select ownership for new copies; they never backfill historical copies.

The request/destination ledgers commit before network dispatch and bind the source store namespace. They retain original envelopes independently of normal message TTL; this change introduces no automatic deletion. Runtime job-control flags are excluded from durable envelopes. The selected backup includes `mailbox_store`, all ledgers, offline registrations/name fences, native-child evidence, archive quarantine, messages and job routes under one stable snapshot boundary. Restore the complete selected group and archive together, including the original namespace. Partial imports with another store's namespace remain preserved but blocked. Legacy supplemental job routes merge by explicit original columns; their new namespace stays empty, and they cannot falsely settle a new report.

Retained readers can defer schema 13 through the existing compatibility mechanism; mailbox registration/storage/read/claim/ACK fail closed until admission. Older binaries refuse the future schema. Protocol 5 symmetrically refuses old local clients/brokers before mailbox effects; protocol 4 lacked per-copy namespace ACK proofs. Initial auth never requests daemon handover, and mismatch stays latched pending an owner-coordinated restart. `mailboxProvenanceV1` separately refuses intermediate remote hosts which advertised native ownership but still collapsed outbound copies into local inbox authority. All three remote ownership capabilities apply before send/receipt effects, including restart/retry. No automatic downgrade, native fallback, installed daemon replacement or upgrade launch is performed.

Fresh exact-name, broadcast, notification and authorized-transfer copies use that evidence while the recipient is offline. Proven new native traffic remains readable and acknowledgeable; it does not depend on absence of a hosted field. Native consumption uses `native-copy:v1` plus the persisted copy identity, containing its original recipient and verified native session/registration provenance. A rename or new registration ID does not rewrite that original proof. Independent native broadcast copies cannot consume one another through a shared configured name or session. Historical shared name/session marks stay inspectable but cannot suppress or acknowledge either kind of successor's mail. Hosted binding-scoped journals retain their same-binding recovery semantics. Queued native ACKs carry the original per-copy proof, and broker write retries fence the captured registration before any consumption effect.

The owner approved the local core protocol change from 2 to 3 (AB-45842194). Exact `checkAuth` equality refuses both old-client/new-broker and new-client/old-broker combinations before registration or mailbox access. Mismatch diagnostics identify the broker/client protocols and require an owner-coordinated upgrade. Inspect the original bytes and independently prove the intended binding before designing a recovery grant. Never replace ambiguous bindings from the current name registry. This intentionally blocks some legitimate old native mail and old lost-ACK recovery until ownership can be proved.

The fixes use one typed ownership contract rather than a native class exemption.

`recipient-ownership.ts` defines disjoint session, process, job and native-child identities. A native provider/session identity includes the agent and exact session ID, remains stable across MCP/CLI reconnection and excludes display name/registration ID. With no session ID, a process identity requires agent, CLI PID, creation identity and physical project path; PID reuse or a changed creation identity/project cannot inherit it. Exact process-scoped recovery or an explicitly reviewed alias grant remains available as a separate recovery concern. Job owners include the unique job incarnation ID and agent; supervisor grants separately govern control and survive an authorized handoff. Child owners additionally include a fresh child incarnation and the captured parent owner. Old child IDs cannot recover another incarnation's send state.

A supplied proof equal to the stored string is insufficient when the claimant's own identity differs. Registration fences include the complete owner and are rechecked inside write retries and replay pumps, including project changes. In-memory send dedupe keys include ownership, so a session update cannot recover another session's cached receipt. Native journals use `native-owner:v2` with verified typed provenance; old name/session/native-copy marks remain intact without consumption attribution. Hosted complete-binding journals retain their original identity and recovery semantics.

Remote pins retain typed native destination and sender ownership before dispatch, along with host ID/fingerprint. The receiver retains sender ownership alongside each copy; replacement senders cannot obtain old receipts or duplicates by reusing a name. Same-session reconnects with new registration IDs remain valid. The separate `nativeOwnershipV1` gate applies to send and receipt traffic in both directions; pairing version and credentials are unchanged.

Per-copy authority now combines **direction, namespace/authenticated host, exact typed owner and copy identity**. A native session/job ID or complete hosted binding is not globally unique. ## Proposed T3-owned remote delegation (design only, parent approval required)

Current `src/network/remote-jobs.ts` constructs `JobRunners`. Its handles, logs, controls and ownership refer to Bridge jobs. They are not remote T3 children and must never be labelled `ownership: "t3"` or substituted for a failed native T3 delegation request.

An explicit remote T3 adapter would require a separate, versioned capability and operation surface, distinct from `remote-job`:

1. The destination T3 app registers a locally scoped adapter and advertises a bounded, expiring capability descriptor through its paired host. Identify the remote host, exact owning T3 parent thread, adapter incarnation, supported operations and protocol version. Negotiate provider/model/option descriptors through that adapter's local `orchestrator_capabilities`; a remote Bridge process cannot impersonate a T3 parent merely from advertised metadata.
2. Establish explicit authorization for a remote principal to request work under that destination parent. Pairing alone grants no T3 task-control authority. Bind the grant to sender host/session, destination host/parent, allowed operations, project/workspace roots, provider/model/options, permission and interaction modes, depth/hop/slot constraints, expiry and revocation. Do not export local bearer credentials. Reject unsupported options or broader permissions; do not translate to a nearby model/effort silently.
3. Persist an operation before its local effect, keyed by authenticated sender and stable `clientRequestId` plus full request digest. Reconnect/retry returns the same result. A lost effect receipt is unknown and reconciled with T3 using the same operation identity; it must not cause a second child or a Bridge-job fallback.
4. The destination adapter calls local T3 `delegate_task`, retaining its real `taskId`, `childThreadId`, provider instance, model and applied options. Return a host-qualified opaque task handle and `ownership: "t3"`. Describe the ownership honestly: a child of the explicitly authorized destination parent; do not claim a native source-parent lineage across PCs unless T3 itself negotiates/supports it. Worktree isolation is performed by T3 on that host, with an explicit base commit and allowed workspace.
5. `status`, result acknowledgement, follow-up, cancellation and questions must use the same authorized task mapping and generation. Prevent cross-parent handle reuse. Return applied-target receipts, durable terminal result context and unknown/refused distinctions; cancellation cannot claim termination without T3 evidence. Preserve ownership/depth/hop guards on every control operation and resume.
6. Before implementation, parent must approve the destination-parent authorization mechanism, adapter lifetime/attachment, cross-host lineage semantics, capability schema, durable reconciliation store, result/context privacy, cancellation behavior and admission limits. Acceptance needs missing/expired capability, revoked grant, mismatched parent, option mismatch, duplicate/unknown spawn, reconnect, depth/hop rejection and wrong-task result fixtures. Live acceptance requires separate owner-authorized hosts and locally scoped adapters.

No remote T3 task protocol or adapter is implemented here.
