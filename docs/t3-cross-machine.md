# Cross-PC T3 messaging acceptance (AB-458)

## Scope and observed defects

Base: `70820a0fd090bd12f8245e9cf7e51db13a78eef0` (`main`). This package changes paired-PC message routing, with no remote task protocol, installed update, provider launch or live other-PC traffic.

On the base, `src/network/link.ts` stripped `PeerInfo.frontend` from peer advertisements. Send frames identified the destination only by its name. A stale advertised name could therefore reach another T3 thread or an ordinary native session without comparing the destination's attested binding. A focused loopback fixture reproduced missing frontend metadata and accepted stale thread/scope/provider/native/missing destinations.

Checking the exact name at network ingress alone was insufficient: `Broker.receiveRemote` also resolves retained aliases. A separate failing fixture showed that an unfenced alias reached a hosted target. The broker now checks the fence again after resolving that alias.

## Implemented routing contract

1. Each local T3 MCP session already attests its frontend to its local T3 host. The network advertises only the validated non-secret binding: `kind`, endpoint scope digest, `threadId`, and `providerInstanceId`. Provider-native `sessionId` remains separate.
2. An optional hello feature, `t3ThreadRouting: true`, negotiates destination fencing. It does not consume a slot in the existing bounded extension capability arrays. Older readers strip the unknown hello field; new senders refuse a T3 send when the destination host does not advertise support. Native-to-native legacy messages remain supported.
3. Before the first wire attempt, the production broker commits the original request owner/content and destination intent to SQLite. The destination records the authenticated host ID and public fingerprint, exact target name and complete frontend; it does not use the transient registration ID as durable ownership. The original envelope is retained too. Restart/retry verifies those immutable values against current authenticated advertisements and refuses a changed host/thread instead of replacing the intent. Direct project-address retries share their original address key; broadcast destinations have separate recipient keys. A negotiated frame then carries `destination: {peerId, frontend?}` using the current matching registration. Hosted senders require an advertised destination. Immediately before dispatch, the sender refreshes its own advertisement so a session reload cannot race receiver authorization.
4. The receiver compares the destination's exact name, registration ID, and complete frontend binding synchronously before broker storage or emission. Hosted-to-native swaps, missing registrations, changed frontend bindings, and missing fences are rejected. The broker repeats the check after retained-alias resolution. A caller refreshes peers and explicitly selects the intended thread after rejection; the transport does not silently retarget/retry.
5. Normal TLS-PSK pairing and advertised-sender authentication remain authoritative. Neither the sender's nor the destination's T3 endpoint URL or authorization grant travels over the paired-PC link. The binding is a routing fence, not a bearer credential.
6. The destination's existing local `T3Waker` submits a pointer to unread Bridge mail through its locally scoped `T3Host.send`. It targets the attested destination thread, never a provider-native session ID. A wrong-thread receipt is an unknown outcome. Refused/unknown wakes leave mail unread and do not fall back to native CLI wake or automatically replay an admitted operation.
7. Each hosted recipient copy persists `recipientFrontend` ownership. Pending reads, deferred hello replay, reply-conflict reads, queue claims, acknowledgements and duplicate receipts must match that ownership. Registration IDs may change; the full scope/thread/provider binding must match. If another live session occupies the former name, the original frontend can reclaim only its owned copies into its newly assigned name. Broadcast copies remain independent. Unmatched copies stay stored. An unfenced legacy message is native mail and cannot be claimed by an arbitrary hosted thread. Internal fresh notifications bind their selected live recipient; recovered envelopes retain their original ownership rather than being reattributed from a reused name. Existing authorized supervisor transfers explicitly bind the new copy; name-only read journals do not acknowledge hosted mail.
8. Message IDs retain the existing content checks and dedupe rules. Reconnect replay recovers the stored receipt without duplicate mail. Source send-state/retry/receipt access checks the retained sender intent, and remote receipt queries cannot switch to a different host with a reused display name. The persisted local wake journal suppresses duplicate wakes across waker reloads, including refused/unknown outcomes. Inbox consumption remains separate from storage and wake acceptance.

## Schema migration and compatibility

SQLite mailbox schema 10 adds `message_frontends`, `send_intents` and `send_destinations`. Existing message and archive rows are neither rewritten nor removed. The binding ledger is keyed by message ID and recipient copy and remains in the primary store when raw mail moves to the existing archive schema; archive lookup/reopen restores the binding. The additive migration uses the existing verified schema/metadata snapshot mechanism and changes no pre-existing rows. No old name/session record is used to invent ownership for legacy mail.

The request/destination ledgers commit before network dispatch. They retain original envelope data for restart reconciliation and remain independent of normal message TTL; this change introduces no automatic deletion. Runtime job-control authorization flags are excluded from durable envelopes. The selected mailbox backup now includes all three ledgers alongside messages, archived messages and job delivery routes. Restore that group together with its archive snapshot; copying raw message rows alone cannot establish frontend ownership. Generic absorbed archival evidence is not authorization to replay mail into a hosted inbox.

Mixed retained readers may defer schema 10 through the existing compatibility mechanism. Local native operation remains available on the older schema; hosted registration and production remote dispatch refuse until the upgrade is admitted and the broker reopens the upgraded schema. Older binaries refuse schema 10. Legacy native-to-native network embedders without a persistence callback retain their native-only API behavior, while production brokers always supply durable destination storage. Old unfenced mail remains inspectable and native-deliverable; it is deliberately withheld from hosted sessions. Incomplete historical hosted send ownership also fails closed rather than attributing an old send to a new frontend.

## Round-two destination and read-recovery audit

Review AB45842175 at `cf6270a9de667066c02f81bd94f93c0993cef640` found that a retained remote project send could enter local resolution after a broker restart, and that frontend nodes still imported name/session read marks. Both were observable with real persistent brokers and node recovery.

The broker now consults immutable request and destination evidence before choosing any current project, group, direct, alias, local or remote route. A retained remote intent addresses its authenticated host ID and original exact recipient; normal network checks still verify the host fingerprint and complete frontend against the current advertisement. A newly available local project cannot receive the payload. If the original remote binding remains online, the retry still reaches it even when a new local project makes fresh address resolution ambiguous. Current ownership changes cannot redirect the original envelope. Stored sends recover their existing copies without dispatching again. Native-child entry points also fence retained identities, and the legacy `send` opcode sends explicit message IDs through tracked recovery instead of discarding them. Guarded/mode/sibling/dashboard paths were audited for the same shared routing boundary.

A retained request with no stored copy and no saved destination refuses retry rather than discovering a new destination. This includes an interrupted broadcast without complete fan-out evidence. Original data is retained; the caller must inspect the unknown outcome before explicitly submitting a new message identity. This is a conservative recovery limit, not a new remote task protocol. No schema version changes in this round: the router reads the existing schema-10 destination envelopes and request records.

Hosted consumption now uses a versioned journal identity containing `kind`, scope digest, thread ID and provider instance ID. Constructor recovery, hello, session changes, read marking and restart use that same identity, independent of mutable registration names, ephemeral peer IDs and provider-native session IDs. The node snapshots its validated frontend binding. A same-binding restart can recover a lost ACK through the real broker while leaving the next unread message exposed, including after its registration name and native session ID change. Local job-result envelopes also retain the selected frontend, refuse a foreign explicit binding, and consult its scoped read receipt.

Journal compatibility is additive: existing hashed name/session rows remain intact, and legacy JSONL import still retains all original bytes, including malformed tails, in the existing verified bundle and cold originals. New scoped identities use the existing metadata receipt table and deferred journal mechanism; no destructive rewrite or speculative conversion of old marks occurs. Native readers retain their legacy name/session recovery contract. Old marks cannot establish hosted ownership and are never imported into a hosted reader. Consequently, previously consumed hosted mail whose ACK was lost under an older version may be exposed again for explicit consumption; silently hiding unread mail would be unsafe. Mixed old/new frontend readers cannot certify this isolation, so acceptance requires the changed node and broker on both hosts.

Round-two qualified red evidence on the exact review head plus tests only: PID `77572`, 7 failed / 24 passed, exit `1`; expanded production regression set PID `16112`, 11 failed / 24 passed, exit `1`. An additional alternate-opcode audit regression failed before its fix at PID `56904`, exit `1`: legacy `send` discarded a supplied durable ID and accepted changed local routing. The final expanded base run, PID `79088`, failed all 13 new cases while the prior 24 passed, exit `1`. Every runner has a 60-second outer timeout, one Vitest worker, and subprocess/provider launch mocks. The existing 24 regressions remain in every complete focused run.

## Proposed T3-owned remote delegation (design only, parent approval required)

Current `src/network/remote-jobs.ts` constructs `JobRunners`. Its handles, logs, controls and ownership refer to Bridge jobs. They are not remote T3 children and must never be labelled `ownership: "t3"` or substituted for a failed native T3 delegation request.

An explicit remote T3 adapter would require a separate, versioned capability and operation surface, distinct from `remote-job`:

1. The destination T3 app registers a locally scoped adapter and advertises a bounded, expiring capability descriptor through its paired host. Identify the remote host, exact owning T3 parent thread, adapter incarnation, supported operations and protocol version. Negotiate provider/model/option descriptors through that adapter's local `orchestrator_capabilities`; a remote Bridge process cannot impersonate a T3 parent merely from advertised metadata.
2. Establish explicit authorization for a remote principal to request work under that destination parent. Pairing alone grants no T3 task-control authority. Bind the grant to sender host/session, destination host/parent, allowed operations, project/workspace roots, provider/model/options, permission and interaction modes, depth/hop/slot constraints, expiry and revocation. Do not export local bearer credentials. Reject unsupported options or broader permissions; do not translate to a nearby model/effort silently.
3. Persist an operation before its local effect, keyed by authenticated sender and stable `clientRequestId` plus full request digest. Reconnect/retry returns the same result. A lost effect receipt is unknown and reconciled with T3 using the same operation identity; it must not cause a second child or a Bridge-job fallback.
4. The destination adapter calls local T3 `delegate_task`, retaining its real `taskId`, `childThreadId`, provider instance, model and applied options. Return a host-qualified opaque task handle and `ownership: "t3"`. Describe the ownership honestly: a child of the explicitly authorized destination parent; do not claim a native source-parent lineage across PCs unless T3 itself negotiates/supports it. Worktree isolation is performed by T3 on that host, with an explicit base commit and allowed workspace.
5. `status`, result acknowledgement, follow-up, cancellation and questions must use the same authorized task mapping and generation. Prevent cross-parent handle reuse. Return applied-target receipts, durable terminal result context and unknown/refused distinctions; cancellation cannot claim termination without T3 evidence. Preserve ownership/depth/hop guards on every control operation and resume.
6. Before implementation, parent must approve the destination-parent authorization mechanism, adapter lifetime/attachment, cross-host lineage semantics, capability schema, durable reconciliation store, result/context privacy, cancellation behavior and admission limits. Acceptance needs missing/expired capability, revoked grant, mismatched parent, option mismatch, duplicate/unknown spawn, reconnect, depth/hop rejection and wrong-task result fixtures. Live acceptance requires separate owner-authorized hosts and locally scoped adapters.

No remote T3 task protocol or adapter is implemented here.
