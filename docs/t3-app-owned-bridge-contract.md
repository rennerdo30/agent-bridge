# App-owned T3 Bridge adapter contract (AB-458, proposed)

Parent selected this direction on 2026-10-22 JST after reading `bcc7f25387c2c3991b8c998e5fe82ada8b47a479`. This package starts at that clean commit in the same isolated branch. The earlier [injection contract](t3-native-bridge-contract.md), its disabled patch and all receipts remain unchanged. Nothing here enables the feature or closes native acceptance.

## Decision and boundary

The smallest useful proxy is an app-owned messaging service registered as a narrow toolkit on T3's existing authenticated `/mcp` endpoint. T3 owns the Bridge broker connection, registration, frontend and exact app-thread binding. Provider configuration receives no Bridge credential and no additional orchestration grant. Wakes use app-owned, already-scoped T3 services directly.

**The current HTTP caller identity is insufficient to enable this safely.** A bearer authenticates its T3 app scope, not the native Codex loop using it. An inherited parent token plus a matching unsigned `_meta.threadId` is not authenticated proof of a parent call. Existing Bridge lineage admission checks a supplied native identity; it cannot make an untrusted HTTP identity authentic. Even peer discovery and inbox reads remain refused without a trustworthy native-caller discriminator. Removing delegation tools reduces authority but does not fix this identity gap.

The artifact therefore implements only a pure, unregistered contract seam with **no default native attestor**. Its successful fixtures use synthetic privileged proofs. The parent owns any subsequent upstream implementation and the choice of a real caller-authentication mechanism.

## Minimal scope and authority model

An active binding consists of separate values:

- Authenticated T3 environment ID, **app** thread ID, provider instance ID and registry credential-session ID. These come only from the per-request authentication context. External OAuth MCP clients without the native thread binding are refused by this adapter.
- The native root thread ID from the attached provider runtime, never a tool argument or an app thread ID. Every call additionally needs an attested native caller, exact root match and the existing Bridge main-thread lineage admission.
- An immutable broker registration lease and frontend identity, plus an adapter generation. Use a stable environment/app-thread/provider frontend namespace distinct from credential generations. Agree an explicit migration boundary before replacing an earlier sidecar frontend; do not silently take over registrations or unread data.
- A private, explicit server-side opt-in to the five messaging tools. No generic broker opcode, arbitrary frontend, sender, parent, scope token or native-child override is accepted from the provider.

The broker connection belongs to T3, one binding per app scope. Connect to the existing owner-configured broker using Bridge's normal protected authentication mechanism, inside the app-owned runtime only. No Bridge token is returned to a tool, placed in T3 provider config or exported to provider shells. This research did not read that token or configuration. Connection failure must not demand-start a daemon or elect a broker.

An unmodified `BridgeNode` is not a drop-in app adapter: `src/core/node.ts:124,504-539` derives the CLI host PID from `process.ppid`, which would identify T3's parent rather than the Codex session. The follow-on needs a reviewed app-owned session identity/connection port that preserves broker host-lifetime checks, `helloT3` frontend confirmation and durable messaging semantics. Do not spoof a CLI parent, change global process identity or copy the raw IPC protocol into T3. The broker's `helloT3` frontend validation (`src/core/broker.ts:666-672`) does not itself authenticate each native MCP caller.

## Toolkit shape and privilege limits

The prototype exposes only `bridge_peers`, `bridge_pending`, `bridge_read_message`, `bridge_send` and `bridge_send_status`. All five require the same native identity gate; reads can disclose private data. Message reads retain the existing paged-read/acknowledgment rules and are not automatically read-only operations. Sending requires a stable message ID and an opaque server-issued recipient reference, scoped to the originating binding. The real broker port must resolve that reference to a pinned peer/frontend and preserve durable destination ownership through retries, restart and unread replay. The pure port does not implement those storage guarantees.

Do not simply forward Bridge's full MCP `send` handler: `src/mcp/server.ts:1381-1405` includes job broadcasts and running-job follow-up paths. The new reduced dispatcher must exclude them, along with spawn/ask, task management, owner decisions, provider controls and generic dispatch. A text message to an authorized peer remains a message; this adapter must not convert it into a task action. Existing peer/job ownership checks and authorization still apply below the adapter.

At T3, use `McpToolAccess.toLayer` and `toolkitRegistration`. Handler authorization uses the app-owned binding policy and live-caller check, with `readsAsCaller` or `writesWithCapability` as appropriate. Do not add `orchestration` merely to make Bridge handlers work, and do not use `readCaller` as a stand-in for the Bridge identity gate. Current `McpSessionRegistry.issue` already includes orchestration in ordinary provider credentials; this package does not remove that existing authority or claim those credentials become messaging-only. A separate messaging-only credential mode would require an explicit registry capability redesign. No additional provider-side grant is needed for the proposed adapter.

## Lifecycle, callbacks and non-retargeting

Bind only after the session manager has reserved/prepared the current credential and the provider runtime has established the exact native root. Do not register native children as top-level Bridge peers. A T3-owned child has its own app scope and must establish its own reviewed binding.

Capture a particular binding object and broker lease before awaiting authorization or dispatch. After every await preceding an effect, recheck that exact binding/generation. Revocation aborts pending work, detaches event listeners and closes only that session's owned broker connection. An obsolete handle cannot close a replacement. A new bind never substitutes for an old operation, even if the same credential/app thread is deliberately reused. After submission, revocation or disconnection leaves an unknown outcome; do not retry against the new binding or return its private data in the old response.

The production port must enforce the immutable registration at its actual effect boundary; an auto-reconnecting client that silently registers another owner would defeat this check. Persist intended remote destinations and retained inbox ownership under the separate AB-458 routing/storage contract. The prototype's generation checks do not certify real broker persistence.

Wakes are host callbacks with a captured app handle, not provider-callable tools. Journal the pointer-only operation before dispatch, preserve accepted/unknown/submitted receipts, and call the already-scoped `OrchestratorMcpService.sendToThread` or underlying `ThreadManagementService` with the exact bound app thread. Recheck registry generation, app liveness and modes under the actual dispatch boundary. Do not round-trip through HTTP or export an orchestration credential to Bridge. Existing request namespaces are credential-specific; uncertain writes must not be replayed into a replacement namespace.

Task actions remain in T3's existing scoped `delegateTask`, `taskStatus` and `cancelTask` services with their parent/task/mode/depth checks. They are absent from this messaging port and prototype. If a later approved host callback needs one, bind it to that same app scope and owned task at construction; never expose a provider-supplied arbitrary task/thread/parent through the reduced Bridge toolkit. Moving Bridge broker ownership into T3 does not grant Bridge jobs T3 task authority.

## Smallest concrete next package and capability prerequisite

The next implementation package is: retain the pure `BridgeMcpAdapter.ts` seam; add `BridgeMcpService.ts` plus scoped toolkit/tools/handlers/tests; wire its single service through `McpHttpServer.ts`, `server.ts`, `ProviderSessionManager.ts` and registry revocation; and add a narrow, reviewed app-owned broker port in the canonical Bridge source. Bridge changes start at the connection/identity port around `src/core/node.ts`, shared messaging dispatch/native admission around `src/mcp/server.ts` and `src/mcp/codex-lineage.ts`, and a host callback port around `src/mcp/t3-wake.ts`. Reuse existing durable journals and broker state instead of copying them into T3. No Bridge production code changed in this research package.

**An upstream T3 integration is unavoidable. A trustworthy native-caller capability is also a prerequisite under the requested HTTP endpoint design.** The inspected existing bearer-plus-metadata path does not supply it. One possible Codex/provider contract would attest the native thread/turn/call, target server/tool, exact arguments or digest, T3 scope/generation, expiry and replay identity over an app-private authority channel, and bind the response to the authorized call. Keys or equivalent grants must remain inaccessible to native-child shells and static inherited MCP configuration. Merely adding another shared token, unsigned header, call-ID lookup or parameter does not meet this contract. Candidate source boundaries are `codex-rs/core/src/mcp_tool_call.rs` and `codex-rs/rmcp-client/src/rmcp_client.rs`, with explicit private app-server negotiation; the secure protocol is not designed or implemented here.

A different app-server-owned dynamic-tool route might avoid new HTTP credentials and carry native IDs on the private provider channel. The comparator has a `DynamicToolCallParams` schema with native thread/turn/call IDs, but the inspected `ThreadStartParams` does not declare `dynamicTools`, and the pinned T3 adapter registers no `item/tool/call` handler. Schema existence is not proof of a supported registration/round-trip primitive. This alternative requires a separate parent design fork and source/runtime capability proof; it is not an assertion that a new Codex protocol change is universally necessary or universally avoidable.

Keep both native injection and proxy forwarding disabled until that caller boundary is proven. Parent review, any upstream implementation and hosted CI remain outstanding; this artifact does not close AB-458.
