# AB-271 private mobile v1 implementation contract

Baseline `a679e53746640c04094070730fb8a29558e1e985`; design and inventory imported by authorship-preserving cherry-picks only. API-INVENTORY.md security takes precedence over DESIGN.md.

## Reconciliation and ownership

- `/mobile/v1` is a fixed typed API, never desktop `/api` forwarding. Job chat resolves to the existing run chat service.
- QR invitations have 256-bit nonces, expire after **120 seconds**, and are consumed atomically. Separate claim credentials and matching desktop confirmation precede one-time device issuance.
- Normal platform trusted HTTPS only. No self-signed bypass, TLS-validation overrides, certificate fingerprints or pinning claims. Private origin/certificate provisioning remains an owner decision.
- Owner access decision: **both LAN and Tailscale**, no public relay/port forwarding. QR carries up to eight exact HTTPS `origins` plus preferred `origin`; every address uses the same PC registry/device credentials/grants. Phone probes safe hello reads to choose a reachable provisioned address; ambiguous writes/refresh/issuance are never retried across addresses. Listener configuration is an inert list of exact private bind addresses/hostnames, origins and TLS options. Tailscale `*.ts.net` certificates may be owner-provisioned via cert/Serve; LAN requires a trusted hostname certificate or an owner-installed trusted CA. No live commands or trust-store changes are performed here.
- Rotating refresh/access/CSRF credentials are hashed server-side. Issuance responses are never persisted. Lost initial credential issuance or refresh response requires desktop revocation and pairing again; credentials cannot be recovered by retrying or switching addresses. Refresh expires absolutely 30 days after initial issuance, not 30 days after each rotation.
- Exact PC/project/entity/generation grants; local questions only; paired-PC reads require existing read trust. Unsupported paired-PC reads remain explicit until a trusted adapter is supplied. No remote answers, approvals, pinning, dismissal, decisions or settings.
- All mutations require UUID idempotency keys. Store-level owner-question CAS and replay records are atomic. Ambiguous operations never replay. Optional session send is disabled in this implementation.
- Content stays in client memory. SecureStore holds only approved gateway origins, preferred origin and device credentials. Background/offline/reconnecting/stale disables writes until a fresh snapshot. No write queue.
- Events are finite bounded catch-up pages with scoped opaque cursors and snapshot reset, rather than an unverified React Native SSE dependency. Foreground polling is sampled, not an audit stream.
- Push adapters/configuration only: generic opaque device-bound hints, tap re-authenticates and fetches current state. No credentials, provider configuration, delivery or physical-device acceptance.

## Implemented operations and limits

Authenticated device API is exactly `/mobile/v1/{me,snapshot,sessions,jobs,questions,chats/<id>,jobs/<id>/steps,questions/<id>,questions/<id>/answer,events,me/session,me/push,notifications/<opaqueId>}`. Public hello returns only static capabilities; pairing claims and refresh have their own restricted credentials. Unknown fields/query keys/duplicate query keys, body on GET, arbitrary upstream paths and forbidden feature routes fail closed. Job chat uses `/api/runs/<run>/chat` internally. Native session IDs are pinned after exact generation resolution; jobs are generation-checked before and after the fixed service read.

Desktop owner page `/mobile/phones` and `/api/mobile/{phones,invitations,claims/<id>,devices/<id>}` are opt-in through `UiOptions.mobileAdmin`, after the existing desktop cookie/Host owner gate. Writes require the exact provisioned loopback origin and random admin CSRF token plus UUID idempotency key; there is no mobile pairing-approval route. QR SVG is generated locally without third-party requests. Desktop grants are initially unselected. Project grants cover local owner questions; sessions and jobs require explicit opaque entity IDs bound to native identity/generation. Paired-PC reads and all cross-PC writes return unsupported in this local adapter.

QR: 256-bit nonce, 120-second expiry, atomic one claimant, separate hashed claim credential, code confirmation, one-time issuance. Invitation records retain the approved HTTPS address list and PC ID. Registry is bound to a stable PC ID. Device access lifetime 5 minutes; rotating refresh expires at the original issuance time plus 30 days (absolute, non-sliding); server stores hashes, and credential response replays contain issued status only. Repeat refresh with a different key revokes the device on retired credential reuse. Lost issuance/rotation cannot recover plaintext credentials: check/revoke that phone on the desktop and pair again, never retry or fail over issuance/refresh. Idempotency ordinary replay tombstones last at least 24 hours (not erased/implicitly reused).

Owner answers, question events and exact replay records commit together in one owner-question store transaction. The original v1 migration and target remain unchanged: `user_version=1`. Store open adds only the independent `mobile_question_answers` table with `CREATE TABLE IF NOT EXISTS`, after the existing migration/version guard; it does not alter existing tables or downgrade a database. This reconciles mobile durability with retained v1 writers, whose constructor rejects higher versions. Old and new handles can coexist. The answer replay ledger is durable and **unbounded**: no expiry, pruning, automatic cleanup or disk-growth bound is implemented. Any future retention policy needs separate review without weakening idempotency. Previously created synthetic v2 fixtures remain preserved and unsupported; no repair, downgrade or recreation is attempted. Answer CAS covers terms and outcome, excluding asynchronous delivery metadata. Gateway event revisions separately include delivery metadata.

Read pages default 20/max 100; request body max 32 KiB; serialized HTTPS responses max 512 KiB; answer max 8,000 characters; chat text max 16,000 with truncation flag. Native read cursor remains inside device/revision/kind/entity-bound opaque gateway cursors; no native path/cursor is accepted from phone input. Native pages are buffered and drained in bounded slices without dropping items. Cursors are bounded to 10,000 in memory/24 hours; unknown, evicted, changed scope/view/epoch/generation returns 410. Event catch-up emits at most one content-free `snapshot.required` invalidation; this deliberate minimal reconciliation replaces incremental upsert/remove streaming in v1. The client refetches authoritative snapshots, replacing removals and revised rows. Source sampling is not a full lifecycle audit.

Rates per minute: hello 30/IP, QR claims 10/IP, claim polls 60/IP, refresh 30/IP, reads 120/device, writes 30/device. Pending invitations max 10. Inert servers cap 32 connections and 10-second header/request timeout; upstream read/write response deadlines are 5 seconds. Shared in-flight sampling avoids duplicate source scans. Expired rate/cursor entries are memory bounded; auth/replay/question data are never cleaned up by this package.

Foreground polls use bounded exponential backoff/jitter; background aborts fetches. Writes require foreground, ready connection, unexpired access, a <=15-second authoritative snapshot and local question-project answer grant. Only an authenticated ready `GET /snapshot` mints/renews write proof on its opaque cursor. The proof is in the existing bounded 10,000-entry cursor cache and binds device ID/revision, gateway epoch, authenticated session/access-credential hash, exact grant hash and authoritative sample time. It expires at 15 seconds; the 24-hour events cursor lifetime does not authorize writes. Events, detail reads and POST sampling never renew proof. Observed offline/stale source state invalidates prior proofs; credential rotation, changed scope or restart requires a fresh authoritative fetch. Writes reauthenticate after the awaited sample and recheck current CSRF/grants. Unrelated session/job/delivery changes do not invalidate an otherwise fresh proof; question `expectedVersion` CAS protects changed terms/outcome. A fresh authorized proof also permits exact durable replay of an already-answered intent; stale proof or changed intent still fails closed. Any changed terms closes client confirmation/reset drafts. Ambiguous writes never replay; ambiguous refresh/issuance requires PC revocation/new pairing. Revocation/grant/view reset clears client content and affected cursors. Chat/step pagination is forward native paging; backward/load-older support is not claimed.

Unexpected gateway exceptions return the generic existing failure DTO and emit only `{ requestId, errorCategory: "unexpected_gateway_exception" }` through the diagnostic sink (constructor fourth argument, sanitized console output by default). No exception message, body, token, path or stack reaches diagnostics; expected validation/authentication/CAS faults do not emit them. Diagnostic sink failure cannot change the response.

Push remains unconfigured by default. `provisionMobile().pollQuestionHints()` is an explicit owner-scheduled seam with one in-flight poll; no timer/listener starts automatically. It projects local open questions only, checks current source/grant/device state, encrypts subscriptions with owner-supplied AES-GCM key, coalesces question/device hints and reserves before provider dispatch. The concrete `ExpoPushProvider` adapter uses fixed official HTTPS URLs, enhanced-security token injection, redirect rejection, <=4 KiB generic hints, 100 submissions/second process budget and ticket/receipt states; it never reads credentials itself. Invalid-device submission responses remove subscriptions. Hint TTL 300 seconds, opaque ID bound to device/current grant; native tap reauthenticates and refetches. Scheduling retry-later work, polling/persisting provider receipts and signed build identity must be provided by reviewed owner configuration before live activation. No APNs/FCM/Expo credentials or actual push requests were used. Provider contract verified against https://docs.expo.dev/push-notifications/sending-notifications/.

## Opt-in programmatic host and handover

`prepareMobileDesktopHost(node, config)` is the only broker/node opt-in production entry in this package. It requires this node to own a listening broker with an **already-existing** OwnerQuestionService. Missing service, non-owner node, retirement or ownership loss returns `source_unavailable` before opening the mobile registry. It never initializes, closes or retimes the borrowed question service. Its same-home facade binds `store`, `complete()` and receipt-enriched `list()` to the broker's existing service. `provisionMobile` requires that facade rather than an optional completion callback, and injects one shared configured MobilePush into both gateway registration/tap resolution and hint polling.

Mobile POST commits question CAS/event/exact replay atomically, then invokes existing `OwnerQuestionService.complete()`. Callback failure leaves durable answered intent; the service's unchanged two-second work tick recovers delivery. Service.list() projects current message consumption receipts into snapshots and answer/replay responses. Delivery remains durable-inbox/wake-requested/unconfirmed until existing receipts prove consumption; HTTP success does not establish delivery or implementation acceptance.

The prepared handle supplies `gateway`, `desktopAdmin`, unbound `listeners`, `ready()`, `pollQuestionHints()` and async idempotent `close()`. A caller explicitly injects `desktopAdmin` into DashboardController/hostDashboard at the **exact** configured loopback port. Mobile hosting rejects saved-port mismatch, fallback ports and adoption of another uninjected dashboard. Ordinary unprepared dashboard behavior and routes stay unchanged. Existing authenticated startUi routes provide pairing confirmation and per-device revocation; Phones navigation/config discovery is not shipped in this package.

Broker election can move ownership. Readiness immediately fails on node stop/disconnect/replacement or broker retirement. Disposal disables gateway and desktop-admin operations, closes only owned prepared HTTPS listeners, drains any pending hint poll and closes the private registry **before** the broker closes its question service. The broker disposer remains registered while node shutdown drains work, preventing service-close races. Retained listener handles cannot stay bound after ownership loss, including late activation. The retiring gateway returns `source_unavailable`; the phone enters reconnect and keeps writes disabled. A successor process must explicitly prepare again with the reviewed persistent registry/PC/origin configuration; no automatic host migration, config discovery, listener binding or credential retry is introduced. A new gateway epoch requires a fresh authenticated snapshot before writes. Real process election/HTTPS handover and physical phone reconnect acceptance remain pending; the fixture tests cover the ownership adapter and simulated listener retirement.

See [programmatic host integration](HOST.md) for the concrete caller entry and setup boundary. The owner-facing disabled-by-default config/Phones/startup package requires separate review. No certificates, provider secrets, environment configuration or live services are discovered or activated here.
